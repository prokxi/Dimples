# SPEC-3: Series, Events, Teams & Pairings

Status: Accepted · Owner: prokxi · Last updated: 2026-10-11
Covers: PRD FR-20 – FR-26 · Milestone: M1 · Depends on: SPEC-1 (golfers), SPEC-2 (courses)

## 1. Goal

A golfer creates a tournament series, invites friends with a link, forms teams, plans events on
courses, and lets Dimples create the matches. When an organiser starts an event, its course data,
handicaps and pairings are frozen, so scores can be entered (SPEC-5) and evaluated (SPEC-4, SPEC-6).

A single tournament is a series with one event.

## 2. User stories

- **US-1** As a golfer, I create a series with a name, a period, the number of events and the points per result. I become its organiser.
- **US-2** As an organiser, I share an invite link; friends who open it join the series directly.
- **US-3** As an organiser, I make other members organisers, or remove that role again.
- **US-4** As an organiser, I form teams that stay fixed for the whole series.
- **US-5** As an organiser, I plan an event: date, course, tee, 18 holes or a nine, format, handicap allowance and pairing mode.
- **US-6** As an organiser, I choose who takes part in an event (e.g. someone cannot make it).
- **US-7** As an organiser, I let Dimples create the matches (random, round robin, team nominations) and adjust them by hand.
- **US-8** As an organiser, I start the event; after that, pairings and handicaps no longer change.
- **US-9** As a member, I see the series, its members, teams, events and pairings.
- **US-10** As a player, I leave a series before its first event starts.

## 3. Domain model

Two aggregates: **Series** and **Event**. Events reference their series by ID. Scores are a separate
aggregate (SPEC-5), so many players can enter scores at the same time without conflicts.

### Series (aggregate root)

| Field | Type | Rules |
|---|---|---|
| id | `SeriesId` (UUID) | Generated by the application. |
| name | string | 2–80 characters. |
| startDate / endDate | LocalDate | `startDate` ≤ `endDate`. |
| plannedEventCount | int | 1–50. The number of events cannot exceed it; organisers can raise it. |
| points | `MatchPoints {win, halved, loss}` | Integers 0–10 with win ≥ halved ≥ loss. Default 3 / 1 / 0. |
| scoreEntryMode | enum | Only `CASUAL` in M1 (SPEC-5). |
| members | list of `Membership` | 1–16 active members. |
| teams | list of `Team` | 0 or at least 2. |
| inviteToken | `InviteToken` | 128 random bits, URL-safe Base64. Can be renewed. |
| createdAt, version | | |

**Membership**: `golferId`, `organiser` (boolean), `joinedAt`, `status` (`ACTIVE`, `LEFT`, `REMOVED`).
- In M1 every member plays. Members who only organise are planned for v2.
- At least one active member is an organiser at all times.

**Team**: `id`, `name` (1–40 characters, unique in the series), ordered list of member golfer IDs.
- A member is in at most one team. Members without a team are allowed.
- **Teams are fixed for the series**: once the first event has started, members cannot move between
  teams and teams cannot be deleted. Members without a team (e.g. late joiners) can still be added to a team.

### Event (aggregate root)

| Field | Type | Rules |
|---|---|---|
| id | `EventId` (UUID) | |
| seriesId | `SeriesId` | |
| name | string, optional | Max 80 characters; the SPA shows "Event 3" when empty. |
| date | LocalDate | Within the series period. |
| courseId, teeId | IDs | Must exist. |
| holeSelection | enum | `ALL`, `FRONT_NINE`, `BACK_NINE` (SPEC-2). |
| format | enum | Only `INDIVIDUAL_MATCH_PLAY_NET` in M1 (SPEC-4). |
| handicapAllowancePercent | int | 0–100, default 100. |
| pairingMode | enum | `RANDOM`, `ROUND_ROBIN`, `TEAM_NOMINATIONS`. |
| participants | set of golfer IDs | Active members. Default: all active members. |
| nominations | per team: ordered golfer IDs | Only for `TEAM_NOMINATIONS`. |
| matches | list of `Match {id, playerA, playerB, flight}` | Created by the pairing (section 4.4). |
| byes | list of golfer IDs | Participants without a match in this event. |
| status | enum | `DRAFT`, `STARTED`, `COMPLETED`, `CANCELLED` (section 4.5). |
| snapshot | `EventSnapshot` | Set at start: tee data and handicaps (section 4.5). |
| version | | |

**Flight**: a number 1…n. A flight has at most 2 matches (4 players). Byes are not in a flight.

## 4. Behaviour

### 4.1 Series & members
- Creating a series makes the creator an active member and organiser.
- Only organisers change the series, its members, teams and events. Other members only read.
- A member leaves the series as long as no event of the series has started. After that, only an organiser
  can remove a member. Their past matches and results stay.
- The last organiser cannot leave, give up the role or be removed → 409.
- A series can be deleted while none of its events has started.
- A golfer's account deletion (SPEC-1, 4.7) is blocked while they are the last organiser of a series that has
  not ended yet → 409. Deleted golfers stay listed as "Deleted golfer".

### 4.2 Invite link
- Organisers see and share the link `<app>/join/<inviteToken>`. Renewing the token makes the old link invalid.
- A logged-in golfer who opens the link sees a preview (series name, period, number of members) and joins
  directly. Without an account they register first (SPEC-1) and come back to the link.
- Joining is not possible after the series end date or with 16 active members → 409.
  Joining twice has no effect (already a member).
- A golfer who left or was removed can join again through the link and becomes active again.

### 4.3 Events
- Organisers create events in `DRAFT`. Course, tee, holes, date, format, allowance, pairing mode and
  participants can be changed while the event is a `DRAFT`.
- Changing participants, nominations or the pairing mode removes the existing matches; the organiser generates
  them again.
- A `DRAFT` event can be deleted.

### 4.4 Pairings

The organiser generates matches with the event's pairing mode and can then edit them by hand (swap players,
change flights, set byes). Every participant is in exactly one match or is a bye. Generating again replaces
the matches.

Randomness comes from an injected random generator, so tests are repeatable.

**RANDOM**
- Random pairs among the participants.
- With an odd number of participants, one participant gets a bye: the one with the fewest byes in this series so
  far; ties are broken at random.

**ROUND_ROBIN (over the season)**
- Goal: every player plays every other player once before anyone plays the same opponent again.
- Dimples counts how often each pair has already met in *started* events of the series and chooses the
  pairing with the fewest repeat meetings for this event (first: the highest repeat count of any pair is as low
  as possible; then: the sum of repeat counts is as low as possible). Byes as in RANDOM.
- Ties are broken in favour of the next round of a circle-method schedule over the series' members (an ordering
  fixed when the first round robin event is generated). This guarantees: with full attendance and an even number
  *n* of players, after *n − 1* events everyone has played everyone exactly once. After that, the next round starts
  and pairs meet a second time.
- With up to 16 members, the best pairing can be found by checking all possible pairings.

**TEAM_NOMINATIONS**
- Requires exactly 2 teams in the series.
- Per event, the organiser sets the order of each team's nominated players (#1, #2, …). Only participants can be
  nominated. Both teams nominate the same number of players.
- Match *i* = team A's #*i* against team B's #*i*.
- Participants who are not nominated get a bye.

**Flights**
- Generated matches get flights in order: matches 1 and 2 in flight 1, matches 3 and 4 in flight 2, and so on.
  The organiser can change them.

### 4.5 Event lifecycle

| From | Action | To | Conditions |
|---|---|---|---|
| – | create | `DRAFT` | Number of events < `plannedEventCount`. |
| `DRAFT` | start | `STARTED` | At least one match; every match player has a Handicap Index on the event date. |
| `STARTED` | complete | `COMPLETED` | All matches have a result (SPEC-5). |
| `STARTED` | cancel | `CANCELLED` | Results of a cancelled event don't count. |
| `COMPLETED` | reopen | `STARTED` | To correct scores (SPEC-5). |

When an organiser **starts** an event, Dimples takes the snapshot:
- The tee data for the hole selection: Course Rating, Slope Rating, par, and par and stroke index per hole (SPEC-2).
- Per match player: the Handicap Index on the event date (SPEC-1). The Course Handicap and Playing Handicap are
  calculated from it as described in SPEC-4 and stored too.

After the start, the event setup, matches and snapshot don't change, even if the course or a Handicap Index changes.
If the start fails, the response lists the reasons (e.g. which players have no Handicap Index).

## 5. REST API

All endpoints are under `/api/v1` and need an authenticated golfer.
- Series and events are visible only to **active members** → 404 for everyone else.
- Changing actions need the organiser role → 403 for members who are not organisers.

| Method & path | Who | Success | Errors |
|---|---|---|---|
| `POST /series` | any golfer | 201 + `Location` | 400 |
| `GET /series?page&size` | any golfer (own series) | 200 page | – |
| `GET /series/{id}` | member | 200 `SeriesResponse` (incl. members and teams) | 404 |
| `PUT /series/{id}` | organiser | 200 | 400, 403, 404, 409 |
| `DELETE /series/{id}` | organiser | 204 | 403, 404, 409 |
| `PUT /series/{id}/members/{golferId}` (`{organiser}`) | organiser | 200 | 403, 404, 409 last organiser |
| `DELETE /series/{id}/members/{golferId}` | organiser, or the member themselves (leave) | 204 | 403, 404, 409 |
| `GET /series/{id}/invite` | organiser | 200 `{token, url}` | 403, 404 |
| `POST /series/{id}/invite/renew` | organiser | 200 `{token, url}` | 403, 404 |
| `GET /invites/{token}` | any golfer | 200 `InvitePreviewResponse` | 404 |
| `POST /invites/{token}/join` | any golfer | 200 `SeriesResponse` | 404, 409 |
| `POST /series/{id}/teams` | organiser | 201 + `Location` | 400, 403, 404, 409 |
| `PUT /series/{id}/teams/{teamId}` | organiser | 200 | 400, 403, 404, 409 |
| `DELETE /series/{id}/teams/{teamId}` | organiser | 204 | 403, 404, 409 |

| `POST /series/{id}/events` | organiser | 201 + `Location` | 400, 403, 404, 409 |
| `GET /series/{id}/events/{eventId}` | member | 200 `EventResponse` (incl. matches, byes, snapshot) | 404 |
| `PUT /series/{id}/events/{eventId}` | organiser, `DRAFT` | 200 | 400, 403, 404, 409 |
| `DELETE /series/{id}/events/{eventId}` | organiser, `DRAFT` | 204 | 403, 404, 409 |
| `PUT /series/{id}/events/{eventId}/participants` | organiser, `DRAFT` | 200 | 400, 403, 404, 409 |
| `PUT /series/{id}/events/{eventId}/nominations` | organiser, `DRAFT` | 200 | 400, 403, 404, 409 |

`complete` and `reopen` are specified in SPEC-5. Members are shown with display name and current Handicap
Index (visible to the other members of the series). All endpoints are documented with OpenAPI annotations.

## 6. Persistence (Flyway)

`V4__create_series.sql`: `series`, `series_member` (PK `series_id, golfer_id`), `team`, `team_member`.
`V5__create_event.sql`: `event`, `event_participant`, `event_nomination` (team, position, golfer),
`event_match` (`id`, `player_a_id`, `player_b_id`, `flight`), `event_bye`, `event_snapshot_hole`
(number, par, stroke index) and snapshot columns on `event` (course rating, slope rating, par) and on
`event_participant` (Handicap Index, Course Handicap, Playing Handicap).
Foreign keys to `golfer`, `course` and `tee`, with indexes on all FK columns. The invite token has a unique index.
A course or tee referenced by an event cannot be deleted (SPEC-2).

## 7. Frontend (SPA)

- **My series** list and **create series**.
- **Series page**: events (with status), members (with organiser badge and Handicap Index), teams, invite link
  with "copy" and "renew".
- **Join page** for the invite link.
- **Event setup** (organisers): event data, participants, nominations, "generate pairings", drag & drop or select
  boxes to edit matches and flights, "start event" with a clear list of what is missing.
- **Event page** (members): matches by flight, with playing handicaps after the start.

## 8. Out of scope

- Members who only organise and don't play (v2).
- Team captains who set their own team's nominations (organisers do it in M1).
- More than 2 teams in `TEAM_NOMINATIONS`; team formats where partners play together (M2).
- Formats other than individual net match play (M2).
- Invites to friends (M2), invites by email (FR-6).
- Tee times or booking.

## 9. Acceptance criteria

Domain
- [ ] AC-1 A series validates name, period, planned event count, points (win ≥ halved ≥ loss) and the 16-member limit.
- [ ] AC-2 A series always has at least one organiser; leaving, removing or demoting the last organiser is rejected.
- [ ] AC-3 Leaving is only possible before the first event started; removal by an organiser keeps past matches.
- [ ] AC-4 Teams: a member is in at most one team; after the first event started, members cannot move and teams cannot be deleted.
- [ ] AC-5 An event's date is within the series period, and the number of events does not exceed `plannedEventCount`.
- [ ] AC-6 RANDOM pairs all participants; with an odd number, the participant with the fewest byes gets the bye.
- [ ] AC-7 ROUND_ROBIN: with full attendance and n = 4, 6, 8 and 10 players, after n − 1 events every pair has met exactly once; event n repeats pairs only then.
- [ ] AC-8 ROUND_ROBIN with changing attendance chooses the pairing with the fewest repeat meetings (highest repeat count first, then the sum).
- [ ] AC-9 TEAM_NOMINATIONS pairs #i against #i, requires 2 teams and equal numbers of nominations, and gives non-nominated participants a bye.
- [ ] AC-10 Manual pairings are valid only if every participant is in exactly one match or is a bye, and flights have at most 2 matches.
- [ ] AC-11 Changing participants, nominations or the pairing mode of a draft removes its matches.
- [ ] AC-12 The lifecycle allows only the transitions in section 4.5; starting fails with reasons when a player has no Handicap Index.
- [ ] AC-13 The snapshot taken at start does not change when the course or a Handicap Index changes later.

Service & API
- [ ] AC-14 Non-members get 404 for the series, its events and its invite endpoints; members who are not organisers get 403 for changes.
- [ ] AC-15 Joining through a valid link adds the golfer directly; renewed tokens make old links return 404; joining a finished or full series returns 409.
- [ ] AC-16 Account deletion of the last organiser of a running series returns 409 (extends SPEC-1).
- [ ] AC-17 A course or tee used by an event cannot be deleted (409, extends SPEC-2).
- [ ] AC-18 Persistence round trip for series (members, teams) and events (participants, nominations, matches, byes, snapshot).
- [ ] AC-19 All endpoints are in the OpenAPI spec.

## 10. Decisions

Decided on 2026-10-11:
- Invite links: join directly.
- Every member plays in M1; non-playing organisers in v2.
- Leaving only before the first event starts; afterwards organisers remove members, results stay.
- Teams are fixed for the series; organisers set nominations.
- Round robin over the season; when there are more events than opponents, pairs meet again.
- A bye gets 0 points (SPEC-6).
- Handicaps, tee data and pairings are frozen when the organiser starts the event.
- At most 16 active members per series.
